# 数据抽象与内存

覆盖 `tensor/` 与 `memory/` 两层：数据怎么描述、内存怎么来、
以及贯穿两者的所有权模型。

---

## 一、Shape

`Shape` 在构造时算出**行主序（C-order）stride**：

```cpp
tensor::Shape s({2, 3, 4});   // numel = 24, strides = {12, 4, 1}
```

`strides_` 目前还没有消费者——`Tensor` 只支持连续布局。它是为后续的
多维索引 / 广播预留的。

### 零长度维度是合法的

构造时算 stride 做的是 `stride /= dimensions_[i]`。任一维为 0 时 `numel_`
已经是 0，这一步就是 **0/0 整数除零**——不是返回错误，是 SIGFPE 直接杀进程
（实测退出码 136）。

零长度维度在真实数据里很常见：空交易日、没有标的通过筛选、空窗口。

**约定**：该维为 0 时 stride 语义上无定义（根本没有元素可寻址），显式置 0，
让空张量能正常构造与传递。这是"空张量合法"这条语义决定的，不是打补丁。

## 二、Tensor 是值类型

```cpp
template <typename T>
class Tensor {
    Shape shape_;
    std::vector<T, memory::PooledAllocator<T>> data_;   // 64 字节对齐
};
```

`Tensor` **按值语义**：拷贝即深拷贝，`auto b = a; b[0] = 1;` 不会影响 `a`。

这个选择是有意的，见下一节。

## 三、所有权模型：什么时候共享，什么时候拷贝

### 问题

计算图执行时，一个节点的输出会被多个下游消费（扇出）。如果边上传的是
`Tensor` 值，一个扇出 N 的节点会被复制 N + 1 次，每次都是一整块内存复制。

### 三个候选方案

| 方案 | 做法 | 结论 |
|---|---|---|
| A | 边上传 `shared_ptr<const Tensor<T>>`，算子签名不变 | **采纳** |
| B | 同 A，但加一层薄视图包装让闭包写法不变 | 否决：引入隐式转换，与项目直白的风格不符 |
| C | 把 `Tensor` 本身改成共享句柄，拷贝变 O(1) | 否决：改变 `Tensor` 的拷贝语义（深→浅），别名语义要重建，爆炸半径最大 |

选 A 的关键：**引用语义只活在 `graph` / `runtime` 两层**，`ops::*` 的对外
签名一个字不改。`Tensor` 保持纯值类型，风险最小。

输出仍按值返回是有意的：算子产出的是**新算出来的张量**，没有拷贝可省。
真正要消除的只是输入的多份副本。

### 安全性建立在哪

整套设计成立的前提是一条约定的不变量：**张量一旦发布即不可变**。

旧代码里这条不变量是"意外"成立的——每个消费者拿到私有副本，想破坏也破坏不了
（同时也无法被测试）。改造后它只由 const 正确性兜着，所以：

- 只提供 `TensorPtr<T> = shared_ptr<const Tensor<T>>` 一个别名，**不提供可变版本**；
- 发布点只有两个（`set_input` 的拷贝构造、算子结果的移动构造），外部可变句柄
  不可能存活。

审计结论：算子层全部 `const Tensor<T>&` 进、`Tensor<T>` 出；backend 内核全部
`const T* in, T* out` 分离缓冲区，从不原地写；全仓无 `const_cast`、无 `mutable`。

### 效果

同一张 1 输入 + 2 算子 + 2 输出的扇出图，每次 `run()` 物化的张量缓冲区：

```
改造前 7 个  ->  改造后 2 个（恰好等于算子节点数）
```

这条现在是常驻断言（`test_no_edge_copies`），期望值从图推导而非硬编码。

## 四、内存从哪来

### 分配器谱系

| 类型 | 用途 |
|---|---|
| `AlignedAllocator<T, Alignment>` | 直接向 OS 申请（`posix_memalign` / `_aligned_malloc`） |
| `MemoryPool` | 按字节尺寸归档的空闲块表，全局单例 |
| `PooledAllocator<T, Alignment>` | 走 `MemoryPool` 的合规分配器，**`Tensor` 的默认分配器** |

对齐固定 64 字节。`PooledAllocator` 只接受 `Alignment <= 64` 的请求
（有 `static_assert` 拦着）。

两个分配器都提供显式 `rebind`——`Alignment` 是非类型模板参数，默认的
`rebind` 推导不出来。这个坑在 `AlignedAllocator` 上踩过一次。

### 为什么 `Tensor` 默认走池化

这不是性能洁癖，是实测逼出来的。图执行每轮都新建/释放中间张量，直连分配会落进
glibc 的 `mmap`/`munmap` 路径：

```
基线        4.39 ms/轮   缺页 2016/轮     ← 2016 × 4KB = 8.06 MB，正好是两个 4MB 输出张量
池化        0.99 ms/轮   缺页    0/轮
```

**4.4 倍**。完整定位过程见 [05-性能与测量](05-性能与测量.md) 第三节。

### 一个被推翻的结论

最初（任务 `#3`）池化是**默认关闭**的，理由是"分配不是瓶颈"——依据是一次
`ops::mul` 1M 只要 0.13 ms。那个判断在**单算子**场景成立，但漏掉了图执行特有的
"每轮重建全部中间张量"模式，两者结论完全相反。

这也是为什么 `benchmarks/` 必须覆盖真实的调用形态，而不只是单算子。

### 池化的三项已知代价

写在这里，因为改动它之前需要知道：

1. **全局单例 + 一把 mutex。** 单线程下开销很低，多线程并发分配会互相争抢。
   按依赖层并行（任务 `#6`）落地前必须先处理，见
   [04-计算图与运行时](04-计算图与运行时.md)。
2. **内存只涨不缩。** 回收的块不还给 OS，直到进程退出才统一释放，峰值占用
   会一直留着。对尺寸多变的长期负载尤其要注意。
3. **静态析构顺序。** `MemoryPool` 是函数局部静态。若使用方在命名空间作用域
   持有 `Tensor`，它的析构可能发生在池销毁之后，那次 `deallocate` 就是
   use-after-destruction。真出现那种用法，得把单例改成"故意不析构"
   （并相应处理 LeakSanitizer 的误报）。

### 分配失败抛异常，不是返回 nullptr

`MemoryPool::allocate` 失败抛 `std::bad_alloc`，与 `AlignedAllocator` 一致。
早先它返回 `nullptr`，两种契约混用——而在这里忽略一次返回值就是空指针解引用。

`deallocate` 则是 `noexcept` 路径（容器依赖这一点），所以池表扩容失败时
退回 OS，不在释放路径上终止进程。

## 五、分配计数探针

`memory::AllocationCounter` 统计经 `AlignedAllocator` / `PooledAllocator`
走出的所有分配。它能当作"物化出的张量缓冲区个数"精确使用，因为：

> `Tensor` 唯一的堆分配就是它的数据缓冲区；`Shape` 走默认分配器，
> `unordered_map` 的节点与 `make_shared` 的控制块同样走默认分配器。

用途是**不依赖基准就能断言"执行期没有多余的张量拷贝"**——
`test_no_edge_copies` 就靠它。计数常开，两个 relaxed 原子自增相对于一次
整块内存拷贝是噪声级开销。

注意它的语义是"发出了一个缓冲区"，无论来自池还是新申请。这样换用池化分配器后
"`run()` 缓冲区数 == 算子节点数"这条不变量依然成立。

## 六、已知局限

- `Shape::strides_` 无消费者（为多维索引 / 广播预留，尚未实现）
- 只支持连续布局，无 view / 切片 / 广播
- 内存回收策略未做（见上"内存只涨不缩"）
- 静态析构顺序的隐患未消除（见上）
