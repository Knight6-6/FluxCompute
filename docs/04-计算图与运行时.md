# 计算图与运行时

覆盖 `graph/` 与 `runtime/` 两层。这一层是"引用语义"唯一允许存在的地方
（另一处是 `memory`/`tensor` 的分配，见 [02](02-数据抽象与内存.md)），
所以本文的重点是**数据流与所有权**。

---

## 一、Node：节点长什么样

```cpp
template <typename T>
struct Node {
    using OpFn = std::function<tensor::Tensor<T>(
                     const std::vector<tensor::TensorPtr<T>>&)>;

    std::size_t id;
    std::string name;
    NodeType type;                                 // Input / Operator / Output
    std::vector<std::shared_ptr<Node>> inputs;     // 强引用
    std::vector<std::weak_ptr<Node>> outputs;      // 弱引用
    OpFn op;                                       // 未绑定时为空
};
```

三个设计点：

**1. `op` 承载"输入张量 → 输出张量"的可执行闭包。** 标量参数（shift 的偏移、
窗口大小等）在**绑定阶段按值捕获**进闭包。这样异构算子的签名被统一成一种，
图不需要认识任何具体算子。

**2. `inputs` 强引用、`outputs` 弱引用。** 这不是随手写的：如果双向都用
`shared_ptr`，`add_edge(a, b)` 会让 a 与 b 互持，形成所有权环，节点对象
永远无法释放（这个泄漏是 LSan 抓出来的）。所有权单向朝上游。
使用 `outputs` 前需要先 `lock()`。

**3. 输入是 `TensorPtr<T>`（`shared_ptr<const Tensor<T>>`），
输出按值返回。** 理由见 [02](02-数据抽象与内存.md)：算子产出的是新张量，
没有拷贝可省；要消除的是输入的多份副本。

## 二、Graph：建图与拓扑排序

职责只有三件：建节点、连边、绑定算子。

```cpp
auto in  = g.create_node("Input(Close)", NodeType::Input);
auto sh  = g.create_node("Operator(Shift)", NodeType::Operator);
auto out = g.create_node("Output(Factor)", NodeType::Output);

g.add_edge(in, sh);
g.add_edge(sh, out);

g.bind_op(sh, [](const std::vector<tensor::TensorPtr<float>>& ins) {
    return ops::shift(*ins[0], /*offset=*/1);
});
```

`bind_op` 会校验目标必须是 `Operator` 类型——**绑定时机在构建期**，
漏绑能在建图阶段就发现，而不是等到执行。

### 拓扑排序

DFS 后序，生产者在前。`visited` 前置标记保证每个节点恰好出现一次。

注意它对**环**不做检测——环会在执行期以"上游输出不可用"的形式暴露
（见下）。这是有意的：建图期不必多一次全图遍历。

## 三、Executor：执行模型

```cpp
runtime::Executor<float> ex;
ex.set_input(in_node, close);   // 注入输入，跨 run 保留
ex.run(graph);                  // 顺序执行整个图
auto factor = ex.get_output(out_node);
```

### run() 的数据流

```
1. values_.clear()                       丢弃上轮输出
2. 从 inputs_ 播种 values_                共享句柄，拷贝的是指针不是数据
3. 按拓扑序遍历每个节点：
   - Input     检查数据是否就位，跳过
   - Output    零成本透传上游句柄
   - Operator  收集上游句柄 → 调闭包 → publish 结果
```

### 两个关键实现细节

**Output 节点是零成本透传，但必须先按值取出。** 实现上走一个私有辅助：

```cpp
tensor::TensorPtr<T> lookup(const std::shared_ptr<graph::Node<T>>& node) const;
```

它**按值返回** `shared_ptr`，而不是返回引用。原因：调用方是
`values_.emplace(node->id, lookup(...))`，而 `emplace` 自身的 rehash 会让
任何指向 `values_` 内部元素的引用在执行过程中悬垂。按值返回把这个隐患
交给类型系统消除。

**`publish` 有两个重载，分别对应两种所有权来源：**

```cpp
static tensor::TensorPtr<T> publish(tensor::Tensor<T>&& t);        // 算子新算出的，移动
static tensor::TensorPtr<T> publish(const tensor::Tensor<T>& t);   // set_input 进来的，拷贝
```

移动版零深拷贝：`Tensor` 的移动构造是 `noexcept` 且真的窃取 `vector` 的
缓冲区指针（`AlignedAllocator` / `PooledAllocator` 都是空类，
`is_always_equal` 成立）。拷贝版用在 `set_input`——那次拷贝**同时承担所有权
与不可变性两个职责**：所有权在调用方手里，而图持有的副本必须独立于调用方
之后的写入，否则"发布后不可变"当场破裂。

### 校验

| 情况 | 行为 |
|---|---|
| Input 节点没有数据 | 抛 `runtime_error` |
| Operator 节点没绑定 op | 抛 `runtime_error` |
| Output 节点输入数 ≠ 1 | 抛 `runtime_error` |
| 上游输出不可用（环或排序 bug） | 抛 `runtime_error` |
| 取不存在的节点输出 | 抛 `runtime_error` |

`run()` 可重复调用：`inputs_` 保留，`values_` 每轮重建。

### `get_output` 返回持有所有权的句柄

返回类型是 `TensorPtr<T>` 按值，**不是引用**。

这不只是风格问题。原实现返回 `values_` 内部引用，第二次 `run()` 里的
`values_.clear()` 会让它悬垂——测试代码已经踩到了，只因之后没再用而侥幸通过。
改为按值返回后，持有即有效，**跨 run 也成立**；语义从"未定义行为"变成了
明确的"快照"。这条有回归测试钉着。

### 内部容器的一个约定

`inputs_` / `values_` **永远不要用 `operator[]` 读**。`TensorPtr` 可默认构造，
`operator[]` 在未命中时会静默插入一个 null 指针，随后在算子闭包的 `*ins[0]`
处空解引用崩溃。一律用 `find()`，未命中抛异常。

（这是零拷贝改造引入的用法安全性净退步：旧代码里 `Tensor` 不可默认构造，
编译器会拦住误用；现在拦不住了，只能靠约定 + 一个显式的 null 检查。）

## 四、线程池的归属：一个刻意留的空白

**Executor 目前不持有任何线程池，`run()` 是纯顺序执行。**

早先 `ThreadPool` 是 `Executor` 的值成员，而当时一个算子都还没并行。代价是
实打实的：每构造一个 `Executor` 就起满 `hardware_concurrency` 个线程
（实测进程线程数 1 → 17，12 个 `Executor` 并存到 193）。

更麻烦的连带后果：`ThreadPool` 持有 `vector<thread>` 且声明了析构函数，
导致 `Executor` 既不可拷贝也不可移动——连 `std::vector<Executor<float>>`
都编不过。

**决定**：`Executor` 不再持有线程池，只剩下两个 map，因此可以廉价创建、
自由拷贝/移动。`ThreadPool` 本身保留在头文件里作为可用工具。

并行调度落地时再引入，届时才有消费者，也才谈得上决定它的归属：
每个 Executor 一个 / 外部注入 / 进程级共享。在没有消费者之前先定这个是空想。

当前有两条 `static_assert`（可移动 / 可拷贝）作为防线：若有人把 `ThreadPool`
按值塞回 `Executor`，会立刻编译失败。

## 五、并行调度（未实现）的前置条件

按依赖层并行是 README 架构图里画了的下一步，但动手前有两个前置：

### 1. 先量，再优化

并行**是否更快**需要基准确认。README 原则 #4 明确要求"不在没有 Benchmark 的
情况下盲目优化"。基准基建已就绪（[05](05-性能与测量.md)），但目前没有多核
场景的数据。

### 2. `MemoryPool` 的全局锁会变成争抢点

`Tensor` 的默认分配器是 `PooledAllocator`，它背后是一把**全局 mutex**。
单线程下开销很低，但 16 个线程同时分配会互相争抢——很可能把并行的收益吃掉。

落地前需要先把池改成分片锁或线程本地。这是
[02-数据抽象与内存](02-数据抽象与内存.md) 里记录的第 1 项代价。

### 并行本身的正确性约束

- 只并行**节点级**，不动各内核内部的循环语义——这样结果确定
  （同层节点各写自己的输出，不共享可变状态）；
- 共享张量的引用计数本身是线程安全的（`shared_ptr` 保证），这正是把边上
  改成共享句柄的收益之一；
- 拓扑排序需要改成分层（同层无依赖），目前是扁平的 DFS 后序。

## 六、已知局限

- 只有顺序执行；无异步、无调度器
- 拓扑排序是递归 DFS，极深的图有栈溢出风险
- 环不做建图期检测，靠执行期报错
- 无算子融合、无内存复用（中间张量在 `values_.clear()` 时才统一释放）
- `Node::outputs` 目前只写不读（无消费者）
