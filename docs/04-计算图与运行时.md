# 计算图与运行时

覆盖 `graph/` 与 `runtime/` 两层。这一层是"引用语义"唯一允许存在的地方
（另一处是 `memory`/`tensor` 的分配，见 [02](02-数据抽象与内存.md)），
所以本文的重点是**数据流与所有权**。

---

## 一、Node：节点长什么样

```cpp
template <typename T>
struct Node {
    using OpFn = std::function<tensor::Tensor<T>(
                     const std::vector<tensor::TensorPtr<T>>&)>;

    std::size_t id;
    std::string name;
    NodeType type;                                 // Input / Operator / Output
    std::vector<std::shared_ptr<Node>> inputs;     // 强引用
    std::vector<std::weak_ptr<Node>> outputs;      // 弱引用
    OpFn op;                                       // 未绑定时为空
};
```

三个设计点：

**1. `op` 承载"输入张量 → 输出张量"的可执行闭包。** 标量参数（shift 的偏移、
窗口大小等）在**绑定阶段按值捕获**进闭包。这样异构算子的签名被统一成一种，
图不需要认识任何具体算子。

**2. `inputs` 强引用、`outputs` 弱引用。** 这不是随手写的：如果双向都用
`shared_ptr`，`add_edge(a, b)` 会让 a 与 b 互持，形成所有权环，节点对象
永远无法释放（这个泄漏是 LSan 抓出来的）。所有权单向朝上游。
使用 `outputs` 前需要先 `lock()`。

**3. 输入是 `TensorPtr<T>`（`shared_ptr<const Tensor<T>>`），
输出按值返回。** 理由见 [02](02-数据抽象与内存.md)：算子产出的是新张量，
没有拷贝可省；要消除的是输入的多份副本。

## 二、Graph：建图与拓扑排序

职责只有三件：建节点、连边、绑定算子。

```cpp
auto in  = g.create_node("Input(Close)", NodeType::Input);
auto sh  = g.create_node("Operator(Shift)", NodeType::Operator);
auto out = g.create_node("Output(Factor)", NodeType::Output);

g.add_edge(in, sh);
g.add_edge(sh, out);

g.bind_op(sh, [](const std::vector<tensor::TensorPtr<float>>& ins) {
    return ops::shift(*ins[0], /*offset=*/1);
});
```

`bind_op` 会校验目标必须是 `Operator` 类型——**绑定时机在构建期**，
漏绑能在建图阶段就发现，而不是等到执行。

### 拓扑排序

DFS 后序，生产者在前。`visited` 前置标记保证每个节点恰好出现一次。

注意它对**环**不做检测——环会在执行期以"上游输出不可用"的形式暴露
（见下）。这是有意的：建图期不必多一次全图遍历。

## 三、Executor：执行模型

```cpp
runtime::Executor<float> ex;
ex.set_input(in_node, close);   // 注入输入，跨 run 保留
ex.run(graph);                  // 顺序执行整个图
auto factor = ex.get_output(out_node);
```

### run() 的数据流

```
1. values_.clear()                       丢弃上轮输出
2. 从 inputs_ 播种 values_                共享句柄，拷贝的是指针不是数据
3. 按拓扑序遍历每个节点：
   - Input     检查数据是否就位，跳过
   - Output    零成本透传上游句柄
   - Operator  收集上游句柄 → 调闭包 → publish 结果
```

### 两个关键实现细节

**Output 节点是零成本透传，但必须先按值取出。** 实现上走一个私有辅助：

```cpp
tensor::TensorPtr<T> lookup(const std::shared_ptr<graph::Node<T>>& node) const;
```

它**按值返回** `shared_ptr`，而不是返回引用。原因：调用方是
`values_.emplace(node->id, lookup(...))`，而 `emplace` 自身的 rehash 会让
任何指向 `values_` 内部元素的引用在执行过程中悬垂。按值返回把这个隐患
交给类型系统消除。

**`publish` 有两个重载，分别对应两种所有权来源：**

```cpp
static tensor::TensorPtr<T> publish(tensor::Tensor<T>&& t);        // 算子新算出的，移动
static tensor::TensorPtr<T> publish(const tensor::Tensor<T>& t);   // set_input 进来的，拷贝
```

移动版零深拷贝：`Tensor` 的移动构造是 `noexcept` 且真的窃取 `vector` 的
缓冲区指针（`AlignedAllocator` / `PooledAllocator` 都是空类，
`is_always_equal` 成立）。拷贝版用在 `set_input`——那次拷贝**同时承担所有权
与不可变性两个职责**：所有权在调用方手里，而图持有的副本必须独立于调用方
之后的写入，否则"发布后不可变"当场破裂。

### 校验

| 情况 | 行为 |
|---|---|
| Input 节点没有数据 | 抛 `runtime_error` |
| Operator 节点没绑定 op | 抛 `runtime_error` |
| Output 节点输入数 ≠ 1 | 抛 `runtime_error` |
| 上游输出不可用（环或排序 bug） | 抛 `runtime_error` |
| 取不存在的节点输出 | 抛 `runtime_error` |

`run()` 可重复调用：`inputs_` 保留，`values_` 每轮重建。

### `get_output` 返回持有所有权的句柄

返回类型是 `TensorPtr<T>` 按值，**不是引用**。

这不只是风格问题。原实现返回 `values_` 内部引用，第二次 `run()` 里的
`values_.clear()` 会让它悬垂——测试代码已经踩到了，只因之后没再用而侥幸通过。
改为按值返回后，持有即有效，**跨 run 也成立**；语义从"未定义行为"变成了
明确的"快照"。这条有回归测试钉着。

### 内部容器的一个约定

`inputs_` / `values_` **永远不要用 `operator[]` 读**。`TensorPtr` 可默认构造，
`operator[]` 在未命中时会静默插入一个 null 指针，随后在算子闭包的 `*ins[0]`
处空解引用崩溃。一律用 `find()`，未命中抛异常。

（这是零拷贝改造引入的用法安全性净退步：旧代码里 `Tensor` 不可默认构造，
编译器会拦住误用；现在拦不住了，只能靠约定 + 一个显式的 null 检查。）

## 四、线程池的归属：一个刻意留的空白

**Executor 目前不持有任何线程池，`run()` 是纯顺序执行。**

早先 `ThreadPool` 是 `Executor` 的值成员，而当时一个算子都还没并行。代价是
实打实的：每构造一个 `Executor` 就起满 `hardware_concurrency` 个线程
（实测进程线程数 1 → 17，12 个 `Executor` 并存到 193）。

更麻烦的连带后果：`ThreadPool` 持有 `vector<thread>` 且声明了析构函数，
导致 `Executor` 既不可拷贝也不可移动——连 `std::vector<Executor<float>>`
都编不过。

**决定**：`Executor` 不再持有线程池，只剩下两个 map，因此可以廉价创建、
自由拷贝/移动。`ThreadPool` 本身保留在头文件里作为可用工具。

并行调度落地时再引入，届时才有消费者，也才谈得上决定它的归属：
每个 Executor 一个 / 外部注入 / 进程级共享。在没有消费者之前先定这个是空想。

当前有两条 `static_assert`（可移动 / 可拷贝）作为防线：若有人把 `ThreadPool`
按值塞回 `Executor`，会立刻编译失败。

## 五、并行调度

```cpp
runtime::ThreadPool pool(8);
executor.run_parallel(graph, pool);
```

按依赖层执行：同层节点互不依赖，提交到**注入的**线程池，层间做屏障。
线程池由调用方提供——`Executor` 不持有它，归属由使用者决定（见第四节）。

### 5.1 为什么是 opt-in，不是默认路径

实测（16 逻辑核 / 8 物理核）表明**并行未必更快**，收益完全取决于算子类型：

| 图内容 | 串行 | 并行（16 线程） | 加速比 |
|---|---|---|---|
| 16 个逐元素 `mul`（1M float，内存受限） | 4.609 ms | 6.023 ms | **0.77×** |
| 16 个 `sort`（256K float，计算受限） | 52.308 ms | 12.619 ms | **4.15×** |
| 8 个 `sort`（256K float） | 25.187 ms | 5.336 ms | **4.72×** |

逐元素算子本身受内存带宽限制，多核一起跑互相抢带宽；`sort` 这类计算密集的
算子才能真正吃满多核。16 线程只拿到 4.7× 而非 8×，因为这台机器是
8 物理核 + 超线程。

**`Executor` 无法判断一个算子属于哪一类**：闭包是类型擦除的 `std::function`，
没有任何成本信息。所以判断只能交给调用方，`run_parallel` 保持显式调用，
`run()` 仍是默认路径。

### 5.2 实现上的两个关键点

**并行阶段不碰 `values_`。** 多线程并发修改 `unordered_map` 是未定义行为。
实现让每个线程只写自己的槽位（`results[i]`，互不相干的内存位置），
层结束后单线程合并回 `values_`。并行期间 `values_` 只被读（`lookup`），
而读是安全的。

**错误经 future 重抛。** 层内屏障是 `f.get()`，节点里抛出的异常在这里重现，
不会被 worker 静默吞掉——有测试钉着。

`min_nodes_per_layer`（默认 2）：层太窄时不值得付线程调度与同步的开销。

### 5.3 分层：用 Kahn 而不是复用 DFS 后序

`topological_layers()` 是独立实现。DFS 给出的是**全序**，而分层需要按
"何时就绪"分组，两者不是一回事。

这是 `Node::outputs`（弱引用）的**第一个消费者**——它在此之前一直是只写不读的。

有环时抛 `runtime_error`：分层本身就是执行调度的一部分，环必须在这里拦下，
不像拓扑排序那样留给执行期暴露。

### 5.4 正确性约束

- 只并行**节点级**，不动各内核内部的循环语义——同层节点各写自己的输出，
  不共享可变状态，因此结果确定；
- 共享张量的引用计数本身线程安全（`shared_ptr` 保证），这正是把边上改成
  共享句柄的收益之一；
- 并行与串行的结果逐元素一致，含 NaN 处理，有测试覆盖。

### 5.5 验证

```bash
# ThreadSanitizer 是并行代码的必查项——ASan 查不出数据竞争
cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_CXX_FLAGS="-fsanitize=thread -g -O1"
cmake --build build-tsan -j4
setarch "$(uname -m)" -R ./build-tsan/tests/test_executor
```

`setarch -R` 不能省：TSan 在新内核上会因 ASLR 熵过高报
`unexpected memory mapping` 而直接退出，**所有测试都会失败**（包括完全不用
线程的），很容易误判成代码问题。

当前状态：**14 组测试零数据竞争**。

## 六、异步执行

```cpp
auto fut = ex.run_async(graph, pool);   // 提交即返回
// ... 干别的 ...
fut.get();                              // 等待；节点里抛的异常在这里重抛
auto out = ex.get_output(node);         // 就绪后才能取结果
```

### 6.1 三个入口是按两个正交维度划分的，不是模式开关

|  | 同步（调用方等） | 异步（提交即返回） |
|---|---|---|
| **顺序执行** | `run()` | `run_async()` |
| **图内并行** | `run_parallel()` | ——（有意不提供） |

"等不等结果"和"图内要不要并发"互不决定。塞进一个 `run(mode)` 参数既表达不了
组合，又会让 `run(SYNC)` 与 `run_parallel` 变成两个入口做同一件事。

### 6.2 为什么没有"异步 + 图内并行"

**实测：向同一个固定大小的线程池嵌套提交会死锁。** 2 线程的池、2 个外层任务
各提交 1 个子任务，最终**完成 0/4**——两个 worker 都卡在等自己的子任务，而
没有线程能去跑那些子任务。`run_async` 若内部再调 `run_parallel(pool)`，正是
这个形状。

即便不死锁，两处并行叠加也会让线程数超额订阅，通常得不偿失。

需要"同时跑多组任务"时，正确用法是每组内部顺序执行、让多个任务在池里自然并发：

```cpp
for (auto& 参数组 : 参数网格)
    futures.push_back(ex->run_async(graph, pool));
```

实测这个形态（16 组 `sort`，16 线程）：

```
串行 run()          63.130 ms
异步 run_async()    12.372 ms   加速比 5.10x
```

### 6.3 调用方的两条契约

1. **future 就绪前不要碰这个 Executor**：`set_input` / `get_output` / 再次 `run`
   都会与后台线程竞争 `values_`，是数据竞争。注意它等价于"没 run 就取结果"，
   只是异步下不会立刻抛异常，而是静默读到半成品。
2. `*this` 与 `graph` 必须活到 future 就绪。

**为什么不做运行时检查**（比如一个 busy 标志）：那需要给 `Executor` 加原子成员，
而原子不可拷贝——会破坏 `Executor` 可拷贝这条已被 `static_assert` 守住的属性
（见 `test_executor.cpp`）。为一个调用方的逻辑错误付这个代价不划算，故用契约
+ 测试锁定。

## 七、已知局限

- 只有顺序与按层并行两种执行方式；无异步、无跨层流水线
- 并行收益强依赖算子类型，而 `OpFn` 是类型擦除的，`Executor` 无从判断
  （见 5.1）——若要自动决策，需要给算子加成本标注，那是更大的改动
- `MemoryPool` 的全局锁在纯分配场景下退化严重（16 线程 7× 慢），
  真实负载里被计算掩盖，但仍是并行的潜在上限，见
  [02](02-数据抽象与内存.md) 第四节
- 拓扑排序是递归 DFS，极深的图有栈溢出风险
- 环不做建图期检测，靠执行期报错
- **无图级自动算子融合**：`OpFn` 是类型擦除的 `std::function`，图看不出节点
  是否为逐元素、也无从取出其标量函数。融合能力由算子层提供（`map2/3/4`），
  由上层在绑定时写出融合表达式。要自动做需改成可反射的结构化算子描述，
  是方向性决策而非增量改动，见 [03](03-算子与内核.md) 第六节
- 无内存复用（中间张量在 `values_.clear()` 时才统一释放）
