# 设计问题记录

这份文档记录**设计与实现中真正遇到过的问题**：现象是什么、怎么发现的、
为什么值得记下来。不含笔误一类的低级问题——那些看 diff 就够了。

**最终实现方案不在本文。** 每节末尾只给一句结论和链接，方案细节归到对应的
分层设计文档里。两者关注点不同：

- 本文回答"踩过什么坑、怎么发现的"；
- 设计文档回答"现在是怎么设计的、为什么这么设计"。

分层文档的导航见 [README](README.md)。

## 一、计算图边上的张量深拷贝

**现象**：一个扇出 N 的节点，其输出被复制 N + 1 次，每次都是一整块内存复制。

**为什么值得记**：这不是 bug，是数据结构选型导致的隐性开销，不测就看不见。
消除它需要动对外接口，属于"要么早做、要么一直将就"的决策。

**结论**：边上改传共享句柄，`ops::*` 签名一个字不改。扇出图物化缓冲区
7 → 2 个。
→ [02-数据抽象与内存](02-数据抽象与内存.md) 第三节

## 二、Node 的所有权环（内存泄漏）

**现象**：节点对象析构后不释放，LSan 报泄漏。

**怎么发现的**：ASan/LSan 跑测试时暴露，不是看代码看出来的。

**根因**：`inputs` 与 `outputs` 都是 `shared_ptr`，`add_edge(a, b)` 让 a 与 b
互持形成环。

**结论**：`inputs` 强引用、`outputs` 弱引用，所有权单向朝上游。
→ [04-计算图与运行时](04-计算图与运行时.md) 第一节

---

## 三、`get_output` 返回的引用会悬垂

**现象**：返回的引用在第二次 `run()` 之后就失效了，但没有任何机制拦住。

**为什么值得记**：测试代码**已经踩到了**，只因之后没再用它而侥幸通过。
一个"文档注释写明了但没人会记得"的生命周期陷阱。

**结论**：改为按值返回持有所有权的句柄，持有即有效、跨 run 也成立，
语义从"未定义行为"变成明确的"快照"。
→ [04-计算图与运行时](04-计算图与运行时.md) 第三节

## 四、零长度维度让进程直接崩

**现象**：`Shape({0})` → SIGFPE，退出码 136。不是返回错误，是**杀进程**。

**根因**：构造时按行主序算 stride，做的是 `stride /= dimensions_[i]`。
任一维为 0 时 `numel_` 已经是 0，这一步就是 0/0 整数除零。

**为什么值得记**：零长度维度在真实数据里很常见（空交易日、没有标的通过筛选），
而这类输入最容易在测试里被漏掉。

**结论**：该维为 0 时 stride 语义上无定义，显式置 0，空张量合法。
→ [02-数据抽象与内存](02-数据抽象与内存.md) 第一节

## 五、单位元不能有默认值

**现象**：通用归约若用 `T{}`（即 `0`）当默认单位元，**全负切片求最大值会
取到错误的 0**。

**为什么值得记**：整数 `T` 没有 NaN，这个错误不会被任何 NaN 检查拦住。
这个坑在写 `max` / `min` 时就踩过一次，所以通用形式直接把它做成必填参数。

**结论**：单位元是必填参数，不做兜底。测试正反两面都断言。
→ [03-算子与内核](03-算子与内核.md) 第 2.1 节

## 六、NaN 语义在两类算子上是分裂的

**现象**：`sum` / `mean` / `max` / `min` 跳过 NaN，而 `reduce` / `scan` 不跳过。

**为什么值得记**：看起来像不一致，实际是刻意的——专用算子知道 NaN 对各自运算
意味着什么，通用算子拿到的是任意二元算子，无从判断。这与 pandas 一致
（`agg` 传自定义函数时 `skipna` 不生效），但不知道这点的人会当成 bug。

**结论**：分裂是设计，不是缺陷。差异已钉成断言。
→ [03-算子与内核](03-算子与内核.md) 第 2.2 节

## 七、`rolling_std` 的 float 累加几乎是一场灾难

**现象**：用 `T` 累加 `sum` / `sum_sq` 算方差，在真实量级下严重失真：

| 数据量级 | float 累加相对误差 |
|---|---|
| 收益率 ~0.01 | 3.0e-07 |
| 价格 ~100 | **3.4e-02** |
| 价格 ~100 且波动极小 | **1.6e+03** |
| 成交额 ~1e6 | **1.0e+00**（等于没算） |

**为什么值得记**：**测试测不出来**。测试用小数据、干净的整数，float 累加完全
正确。只有真实量级的数据才会暴露。这是"先量后写"救回来的一次。

**结论**：累加器提升到 double，误差降到 ~1e-10；残留局限标注在内核里。
→ [03-算子与内核](03-算子与内核.md) 第三节

## 八、图执行的 75% 时间花在缺页上

**现象**：裸 `shift` + 裸 `mul` 之和 1.09 ms，放进图里执行却要 2.5 ~ 4.3 ms。
尺寸扫描确认额外开销随规模线性增长（约 2.8 ns/元素），不是固定开销。

**怎么发现的**：量缺页——**2016 次/轮**，而 2016 × 4KB = 8.06 MB，
正好是两个 4MB 输出张量。根因是每轮 `run()` 重建中间张量时 glibc 走
`mmap`/`munmap`，每页都要重新 fault。

**为什么值得记**：这是目前信息量最大的一次定位。"分配开销很小"这个直觉
在单算子场景完全正确，在图执行场景完全错误——**两者的结论是相反的**。

**结论**：`Tensor` 默认改走池化分配器，4.39 → 0.99 ms/轮。
→ [02-数据抽象与内存](02-数据抽象与内存.md) 第四节、
[05-性能与测量](05-性能与测量.md) 第四节

## 九、ThreadPool 空转，还把 Executor 拖成不可移动

**现象**：`ThreadPool` 曾是 `Executor` 的值成员，当时一个算子都没并行。
每构造一个 `Executor` 就起满核线程（实测 1 → 17，12 个并存到 193）。

**连带的坑**：`ThreadPool` 持有 `vector<thread>` 且声明了析构函数，
导致 `Executor` 既不可拷贝也不可移动——连 `std::vector<Executor<float>>`
都编不过。这个是写基准时才撞上的。

**结论**：`Executor` 不再持有线程池。归属问题留到并行落地时再定。
→ [04-计算图与运行时](04-计算图与运行时.md) 第四节

## 十、分配器的失败契约不一致

**现象**：`MemoryPool::allocate` 失败返回 `nullptr`，而 `AlignedAllocator`
抛 `std::bad_alloc`——同一层两种契约。

**为什么值得记**：返回 `nullptr` 的约定太容易被忽略，而在这里忽略一次
就是空指针解引用。

**结论**：统一为抛异常。`deallocate` 保持 `noexcept`（容器依赖这一点），
池表扩容失败时退回 OS。
→ [02-数据抽象与内存](02-数据抽象与内存.md) 第四节

## 十一、`#pragma omp simd` 是冗余的

**现象**：同源双目标对照（一份链 OpenMP、一份不链），结果在噪声内相同。

**根因**：`-O3` 的自动向量化本来就命中了这些循环。编译器的向量化报告显示
基线 SSE2 下已用 16 字节向量。

**为什么值得记**：项目从建立起就挂着这些 pragma，一直当作优化在维护，
从未验证过。而真正的杠杆是**目标指令集**（`-march=native` 下 `sum_all` 1M
从 0.63 ms 降到 0.04 ms，约 14 倍）——方向一直讲错了。

**后续（已解决）**：光知道"杠杆是指令集"还不够，直接上 `-march=native` 会
牺牲可移植性。`target_clones` 绕开了这个两难——编译器生成多份实现、运行时
按 CPU 选，实测拿满了 native 的全部收益（`sum` 14.4×）且二进制仍能在旧 CPU 上跑。

但它**只对本身可向量化的内核有效**：同一轮测量里 `ops::max` 一点没变
（1.00×），因为 `extremum` 刻意没加 simd 提示，编译器即便面对 AVX-512 也
向量化不了那个带 NaN 过滤的条件极值。所以属性只加在 `sum_*` / `mean_*` 上，
给 `extremum_*` / `reduce_*` 加只会让二进制多出三份永不生效的副本。

**结论**：pragma 保留无害但别指望它；指令集杠杆用运行时分发拿，opt-in
（依赖 IFUNC，musl / macOS 不支持）。
→ [03-算子与内核](03-算子与内核.md) 第五节

## 十二、测量方法本身的坑

这一节与性能无关，但没有它，前面所有数字都不可信。

### 12.1 编译器会把你想测的东西优化掉

用 `std::vector` 制造分配来测分配器，缓冲区内容无人观察，**分配和清零都被
合法消除了**。测出"1MB 分配 25 ns/次"这种物理上不可能的数字。

更隐蔽的是：池化那一路因为改动全局状态而无法被消除，于是**两边根本不在测
同一件事**，得出"池慢 323 倍"，与真相（池快 1.75~3 倍）方向完全相反。

### 12.2 参照实现不能就是被测算法

验证 `rolling_std` 精度时，第一版参照用的也是同类公式，误差必然是 0——
循环论证，白测一轮。

### 12.3 编译参数不同，结论会反过来

同一个 `sum_all`：项目参数下 0.63 ms，加 `-march=native` 0.04 ms。
拿后者去和别的实现比会得出完全错误的结论。

### 12.4 基准要覆盖真实的调用形态

内存池最初被判定"不值得启用"，依据是一次 `ops::mul` 只要 0.13 ms。
那个判断在单算子场景正确，却漏掉了图执行特有的"每轮重建全部中间张量"模式。

### 12.5 工具用错比不用更糟

拿 1M 元素去跑 `rank`（每切片 O(N²) 的计数法）基准，等于要求 1e12 次比较，
进程直接卡死只能杀掉。跑之前先看一眼算子声明的复杂度。

### 12.6 构建失败时，测试跑的是旧二进制

验证脚本写成：

```bash
cmake --build build | grep -E "error|warning"   # 编译错误走 stderr，grep 没看见
ctest --test-dir build/release                            # 跑的还是上次成功构建的二进制
echo "构建: 零告警"                                # 无条件输出，说了假话
```

结果：**构建是坏的，测试却报全绿**。三个环节各自"看起来正常"，合起来给出
了完全错误的结论。

### 12.7 消毒器在新内核上会因 ASLR 直接退出

TSan 报 `FATAL: unexpected memory mapping` 并退出，**所有测试都失败**——
包括完全不用线程的。这是 TSan 与高 ASLR 熵的已知不兼容，很容易误判成
"并行代码有 bug"。绕过用 `setarch $(uname -m) -R`。

→ 对策与完整案例：[05-性能与测量](05-性能与测量.md) 第三节

## 十三、并行调度不是"做了就好"

**现象**：把同一层的节点并行执行，实测在逐元素算子上**更慢**：

| 图内容 | 串行 | 并行（16 线程） | 加速比 |
|---|---|---|---|
| 16 个逐元素 `mul`（1M，内存受限） | 4.609 ms | 6.023 ms | **0.77×** |
| 8 个 `sort`（256K，计算受限） | 25.187 ms | 5.336 ms | **4.72×** |

**为什么值得记**：这是"README 架构图里画了 Scheduler，所以就该做"的一次反转。
**架构图上有的模块不等于必然的收益**——逐元素算子受内存带宽限制，多核一起跑
只是互相抢带宽；只有计算密集的算子才能真正吃满多核。

更麻烦的是：`Executor` 无法判断一个算子属于哪一类。闭包是类型擦除的
`std::function`，没有任何成本信息，所以"自动决定要不要并行"在当前设计下做不到。

**结论**：并行做成显式的 `run_parallel`，`run()` 仍是默认路径。
→ [04-计算图与运行时](04-计算图与运行时.md) 第五节

## 十四、融合的收益与"自动融合"做不到的原因

**现象**：逐元素链的融合收益很大且随链长增长：

| 表达式 | 分离 | 融合 | 加速比 |
|---|---|---|---|
| `(a+b)*c`（1M） | 0.636 ms | 0.324 ms | 1.96× |
| `(a+b)*c-d`（1M） | 1.134 ms | 0.477 ms | 2.38× |

**为什么值得记**：逐元素算子实测是内存受限的（并行只有 0.92×），所以
**真正的杠杆是减少内存流量，不是提高算力**。这一点决定了优化的方向——
先测出来的那个"并行没用"的结论，恰恰是这里该做融合的理由。

**更值得记的是做不到的那部分**：图级自动融合在当前架构下**做不成**。
`OpFn` 是类型擦除的 `std::function`，图看不出节点是不是逐元素、也无从取出
它的标量函数。真要按元素做类型擦除的间接调用，开销很可能超过省下的流量
——**融合的收益来自省遍历，而类型擦除恰恰把省下的又吃回去**。

要自动做，得把算子从"类型擦除的闭包"改成"可反射的结构化描述"，
或改用编译期表达式模板。那是方向性决策，不是增量改动。

**结论**：由算子层提供融合能力（`map2/3/4`），上层在绑定时写出融合表达式。
→ [03-算子与内核](03-算子与内核.md) 第六节

## 十五、内存池的占用会无界增长

**现象**：池按字节尺寸归档，**尺寸从不重复**的负载会让每个新尺寸都留下一个
永不复用的块——RSS 线性增长，不收敛（实测每轮约 2.3 MB）。

尺寸固定的负载不会：第一轮走遍各尺寸后 RSS 就稳住了。

**为什么值得记**：这是池化设计的固有代价，不是 bug，但**只在特定负载形态下
才暴露**。"筛选后标的数每天不同"在量化里很常见，所以不能只当作极端情况。
另外，这个代价在引入池化时（任务 `#3`）就记在文档里了，但当时**没有量过**——
量了才发现它确实会无界，而不是"停在峰值"。

**结论**：加保留上限（默认 256 MiB，可调），超出部分归还 OS。
→ [02-数据抽象与内存](02-数据抽象与内存.md) 第四节

## 十六、几个还没解决的

- **目标指令集策略**：涉及可移植性，见 [05](05-性能与测量.md) 第五节
- **静态析构顺序**：使用方持有命名空间作用域的 `Tensor` 会踩到
  use-after-destruction，见 [02](02-数据抽象与内存.md) 第四节
- **`MemoryPool` 的全局锁**：纯分配场景下 16 线程退化 7×。真实负载里被计算
  掩盖，但仍是并行的潜在上限——需要先量出它是否真的限制了计算受限场景的
  加速比（4.72× 而非 8× 是否因它而起），再决定要不要改分片锁 / 线程本地
- **并行无法自动决策**：见第十三节，`OpFn` 是类型擦除的，无从判断算子成本
