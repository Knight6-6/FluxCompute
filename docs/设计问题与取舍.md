# FluxCompute 设计问题与取舍记录

这份文档记录的是**设计与实现中真正遇到过的问题**，以及当时的取舍和依据。
不含笔误、拼写一类的低级问题——那些看 diff 就够了。

记录原则：

- 有实测数据的写数据，没有的写明"未验证"，不把推测写成结论；
- 取舍要写清**为什么不是另一个方案**，否则后来者会把取舍当成疏漏重新讨论一遍；
- 已知局限要标出改造点在哪。

---

## 一、零拷贝：引用语义该放在哪一层

### 问题

`Executor` 执行计算图时，张量沿边传递的都是**值拷贝**。`Tensor` 内部是
`std::vector<T, AlignedAllocator>`，拷贝即整块内存复制。一个扇出 N 的节点
被复制 N + 1 次。

### 三个候选方案与取舍

| 方案 | 做法 | 否决理由 |
|---|---|---|
| A | 边上传 `shared_ptr<const Tensor<T>>`，算子签名不变 | **采纳** |
| B | 同上，但加一层薄视图包装让闭包写法不变 | 引入隐式转换，与项目直白的风格不符 |
| C | 把 `Tensor` 本身改成共享句柄，拷贝变 O(1) | 改变 `Tensor` 的拷贝语义（深→浅），别名语义要重建，爆炸半径最大 |

采纳 A 的关键理由：**引用语义只允许活在 graph / runtime 两层**。
`ops::*` 的对外签名（`const Tensor<T>&` 进、`Tensor<T>` 出）一个字不改，
引用不会渗进算子层与张量层。`Tensor` 保持纯值类型，风险最小。

输出仍按值返回是有意的：算子产出的是**新算出来的张量**，没有拷贝可省。
真正要消除的只是输入的多份副本。

### 安全性建立在哪

整套设计成立的前提是一条约定的不变量：**张量一旦发布即不可变**。

旧代码里这条不变量是"意外"成立的——每个消费者拿到私有副本，想破坏也破坏不了
（同时也无法被测试）。改造后它只由 const 正确性兜着，所以：

- 只提供 `TensorPtr<T> = shared_ptr<const Tensor<T>>` 一个别名，**不提供可变版本**；
- 发布点只有两个（`set_input` 的拷贝构造、算子结果的移动构造），外部可变句柄
  不可能存活。

审计结论：算子层全部 `const Tensor<T>&` 进、`Tensor<T>` 出；backend 内核全部
`const T* in, T* out` 分离缓冲区，从不原地写；全仓无 `const_cast`、无 `mutable`。

### 连带的设计决定

**Output 节点改为零成本透传。** 原本 Output 节点会"拷贝 ins[0] 再 move"，
而那个 move 的正确性完全依赖上游那次拷贝。改造后 Output 直接共享上游句柄，
不再白付一次 vector 分配。实现上必须**先经按值返回的 `lookup()` 取出**，
不能把 `values_` 的内部元素直接喂给 `emplace`——rehash 会让那个引用悬垂。

**`get_output` 由返回引用改为按值返回 `shared_ptr`。** 这不只是风格问题：
原实现在第二次 `run()` 里 `values_.clear()` 之后会留下悬垂引用，测试代码
已经踩到了（只因之后没再用而侥幸通过）。改为 shared_ptr 后持有即有效，跨 run
也成立——顺便把一个潜在 UB 变成了明确语义。

### 结果

同一张 1 输入 + 2 算子 + 2 输出的扇出图，每次 `run()` 物化的张量缓冲区：

```
改造前 7 个  ->  改造后 2 个（恰好等于算子节点数）
```

这条现在是常驻断言（`test_no_edge_copies`），期望值从图推导而非硬编码，
任何把边拷贝改回来的改动都会立刻失败。

## 二、算子语义：几个必须显式做出的决定

### 单位元不能有默认值

通用归约 `reduce` 的单位元**必须由调用方给出**，不能靠 `T{}` 兜底。

看起来 `0` 是个合理的默认单位元——对求和确实如此。但求最大值的单位元是
`lowest()`，用 `0` 会让**全负切片取到错误的 0**。整数 `T` 没有 NaN，
这个错误不会被任何 NaN 检查拦住。

这个坑在写 `max` / `min` 时就踩过一次，所以 `reduce` / `scan` 直接把它做成
必填参数。测试里正反两面都断言了（`test_reduce_identity_is_not_optional`）。

### NaN 语义在两类算子上是分裂的，而且是故意的

| | NaN 处理 | 理由 |
|---|---|---|
| `sum` / `mean` / `max` / `min` / `rolling_*` | **skipna**（跳过） | 它们知道 NaN 对各自运算意味着"不参与" |
| `reduce` / `scan`（通用） | **不跳过** | 拿到的是任意二元算子，无从知道它该怎么处理 NaN |

这与 pandas 一致：`sum`/`mean` 默认 `skipna=True`，而 `agg` 传自定义函数时
`skipna` 不生效。

对 `scan` 还有一处更细的差异需要知道：pandas 的 `cumsum` 在 NaN 处**输出 NaN
但继续累加**（`[1, NaN, 3] -> [1, NaN, 4]`），而这里一旦吃到 NaN 之后全是 NaN
（`-> [1, NaN, NaN]`）。要 pandas 语义应当在算子层显式处理 NaN，不该把这个
假设埋进通用内核。差异已钉成断言。

另外 `sum` 的空集语义是 **0**（加法单位元），而 `mean`/`max`/`min` 是 **NaN**。
这也是 pandas 的行为，不是不一致。

## 三、数值稳定性：一个差点静默上线的灾难

### 问题

`rolling_std` 最初打算沿用 `rolling_mean` 的结构，用 `T` 累加 `sum` / `sum_sq`，
方差按 `sum_sq - sum²/n` 算。这在数学上是对的，但**存在灾难性抵消**。

### 实测（对照"先减均值"的稳定两趟算法，取最大相对误差）

| 数据量级 | float 累加 | double 累加 |
|---|---|---|
| 收益率 ~0.01 | 3.0e-07 | 5.6e-16 |
| 价格 ~100 | **3.4e-02** | 9.3e-12 |
| 价格 ~100 且波动极小 | **1.6e+03** | 2.1e-04 |
| 成交额 ~1e6 | **1.0e+00** | 3.2e-10 |

float 累加在成交额量级下误差 **100%**——等于没算。

### 取舍

累加器统一提升到 double（`long double` 除外），并顺带让整数 `T` 也走 double，
避免 `sum_sq` 在整数上溢出。

**这个问题的危险之处在于测试测不出来**：测试用小数据、干净的整数，
float 累加完全正确。只有用真实量级的数据才会暴露。

### 残留局限

均值² / 方差 超过 ~1e7 时 double 也开始丢有效位，要覆盖得换 Welford 递推或
分块两趟算法。但那种数据的 mean/std 比已经超出 float 的表示能力，属于人造输入。
内核里标注了明确的改造点。测试用成交额量级（1e6）的数据对照稳定参照，
相对误差须在 1e-4 内——若有人把累加器退回 float，这条会立刻失败。

## 四、空张量的语义

`Shape` 构造时按行主序算 stride，做的是 `stride /= dimensions_[i]`。
任一维为 0 时 `numel_` 已经是 0，这一步就是 **0/0 整数除零**——
不是返回错误，是 SIGFPE 直接杀进程（实测退出码 136）。

零长度维度在真实数据里很常见：空交易日、没有标的通过筛选、空窗口。

**决定**：该维为 0 时 stride 语义上无定义（根本没有元素可寻址），显式置 0，
让空张量能正常构造与传递。这是"空张量是合法的"这一语义决定的，不是打补丁。

## 五、性能：几个与预期相反的发现

### 5.1 `#pragma omp simd` 是冗余的，真正的杠杆是指令集

项目从建立起就在 backend 内核上挂 `#pragma omp simd`，但从未验证过收益。

**对照实验**：同一个源文件编两份，一份链 OpenMP、一份不链，两组数据几乎完全相同
（部分项不链的反而略快，属噪声）。编译器的向量化报告给出了原因：

```
基线 SSE2：      loop vectorized using 16 byte vectors   <- 已经向量化了
-march=native：  loop vectorized using 64 byte vectors   <- AVX-512
```

`-O3` 的自动向量化本来就命中了这些循环，pragma 没有额外贡献。
而 `-march=native` 带来的是**数量级差异**：`sum_all` 1M 从 0.63 ms 降到 0.04 ms（约 14 倍）。

**结论**：SIMD 的故事一直讲错了重点。真正的杠杆是目标指令集，而这带来的是
可移植性问题（二进制不能在旧 CPU 上跑），需要单独决策，不能靠加 pragma 解决。

### 5.2 内存池确实更快，但分配不是瓶颈

（见下一节的测量陷阱——第一版测出"池慢 323 倍"，是错的。）

修正后：

| 场景 | 直连 | 内存池 | 提升 |
|---|---|---|---|
| 同尺寸 4KB × 200k | 3.761 ms | 2.153 ms | 1.75× |
| 同尺寸 1MB × 20k | 0.518 ms | 0.215 ms | 2.4× |
| 批量 4KB | 1.077 ms | 0.357 ms | 3.0× |

池化在它擅长的场景下确实更快。但**这不构成默认启用它的理由**：

1. 这些数字是纯分配开销。一次 `ops::mul` 1M 是 0.13 ms，其中分配占比很小，
   2~3 倍的分配提速换算到端到端可能只有百分之几；
2. `MemoryPool` 是全局单例 + 一把 mutex，用于按依赖层并行执行会变成争抢点；
3. 池回收的内存不还给 OS，峰值占用会一直留着。

所以 `PooledAllocator` 作为接缝提供，默认不启用。真正的消费者应当是 `#4`
的中间张量 buffer 复用，而不是"所有 Tensor 都走池"。

### 5.3 未解释的生产者：图执行多算子时的额外开销

**现象**（可复现，1M float，Release）：

```
裸 ops::mul                                 0.13 ms
裸 ops::shift                               0.83 ms
图中 1 个 mul                               0.15 ms   <- 与裸调用一致，执行器开销可忽略
图中 1 个 shift                             0.80 ms   <- 同上
图中 2 个算子（扇出 shift + mul）           2.5 ~ 3.9 ms   <- 各部分之和只有 0.96 ms
图中 4 个算子（链式）                       3.9 ms    <- 与 2 个算子几乎一样
```

开销**不是线性于算子数**（2 个算子和 4 个算子差不多），也**不是执行器的固定
开销**（4 个元素的图测出来是 0.000 ms）。

已排除：
- 执行器自身（单算子图与裸调用无差异）
- 页缺失（图执行与裸调用的次要缺页数相当，约 68 次/轮）

同一个图在不同程序里量出 2.5 ms 和 3.9 ms，说明它依赖进程的分配器状态。

**状态：未定位。** 现象可复现，但根因需要 profiler（本环境未装 `perf`）。

嫌疑方向：每次 `run()` 都新建/释放 4MB 张量带来的分配抖动，与缓存行为叠加。
如果确认，`#4`（中间张量 buffer 复用）正好是对症的——这也是把它排在关键路径上的原因。

## 六、测量方法本身的坑

这一节和性能无关，但没有它前面几节的数字都不可信。

### 6.1 编译器会把你想测的东西优化掉

第一版内存基准用 `std::vector<float, Alloc> v(elems);` 制造分配，测出
"1MB 直连分配 200k 次只要 0.127 ms"（25 ns/次）——物理上不可能。
原因是缓冲区内容无人观察，**分配和清零都被合法消除了**。

更隐蔽的是：池化那一路因为改动全局状态而无法被消除，于是两边根本不在测同一件事，
得出"池慢 323 倍"的结论，方向完全相反。

**对策**：直接调 `allocate`/`deallocate` 并触碰首尾元素，让指针逃逸
（`bench_util.hpp` 的 `keep()`）。**没有逃逸的测量等于没测。**

### 6.2 参照实现不能就是被测算法

验证 `rolling_std` 精度时，第一版参照实现用的也是 `double` 累加的同类公式，
于是被测与参照完全相同，误差必然是 0——循环论证。
换成"先减均值"的稳定两趟算法后，才看到真实误差。

### 6.3 编译参数不同，结论会反过来

同一个 `sum_all`：

```
项目当前参数（-O3，基线指令集）  0.63 ms
加 -march=native                0.04 ms
```

拿后者去和别的实现比，会得出完全错误的结论。基准数字必须标注编译参数。

## 七、其他取舍

### ThreadPool 不该被 Executor 按值持有

`ThreadPool` 曾是 `Executor` 的值成员，而当时一个算子都还没并行。代价是实打实的：
每构造一个 `Executor` 就起满 `hardware_concurrency` 个线程（实测进程线程数
1 -> 17，12 个 Executor 并存到 193）。

更麻烦的连带后果：`ThreadPool` 持有 `vector<thread>` 且声明了析构函数，
导致 `Executor` 既不可拷贝也不可移动——连 `std::vector<Executor<float>>` 都编不过。

**决定**：`Executor` 不再持有线程池。并行调度落地时再引入，届时才有消费者，
也才谈得上决定它的归属（每个 Executor 一个 / 外部注入 / 进程级共享）。
在没有消费者之前先定这个是空想。

### 分配器失败应当抛异常，不是返回 nullptr

`MemoryPool::allocate` 原先失败返回 `nullptr`，而 `AlignedAllocator` 抛
`std::bad_alloc`——同一层两种契约。返回 nullptr 的约定太容易被忽略，
而在这里忽略一次就是空指针解引用。已统一为抛异常。

`deallocate` 则是 `noexcept` 路径（容器依赖这一点），所以池表扩容失败时
退回 OS，不在释放路径上终止进程。
