# 架构总览

FluxCompute 是一个**业务无关**的通用 CPU 计算库：底层提供计算能力，上层负责
组合计算逻辑。库本身不理解"因子""策略""订单"这些概念。

本文说明整体分层与各层边界。每一层的设计细节见对应文档：

|---|---|
| [02-数据抽象与内存](02-数据抽象与内存.md) | `Shape` / `Tensor` / 分配器 / 所有权模型 |
| [03-算子与内核](03-算子与内核.md) | 算子层与 backend 的解耦、语义约定、数值稳定性 |
| [04-计算图与运行时](04-计算图与运行时.md) | `Node` / `Graph` / `Executor` / 调度 |

## 一、分层与依赖方向

```
        ┌─────────────────────────────────────────────┐
上层：  │  因子计算 / 回测 / 参数搜索（不属于本库）      │
        └─────────────────────────────────────────────┘
                            ↓
   runtime/  ──  Executor：按拓扑序执行计算图
       ↓
   graph/    ──  Node / Graph：建图、连边、绑定算子、拓扑排序
       ↓
   operator/ ──  算子门面：校验 + 转发，不含循环
       ↓
backend/cpu/ ── 真正的循环实现，SIMD 提示在这里
       ↓
   tensor/   ──  Shape / Tensor：数据抽象
       ↓
   memory/   ──  对齐分配器 / 内存池
```

依赖**单向向下**。`tensor` 不认识 `graph`，`operator` 不认识 `runtime`。

### 各层职责

| 层 | 职责 | 明确不做 |
|---|---|---|
| `memory` | 对齐分配、缓冲复用 | 不理解"张量" |
| `tensor` | 描述数据：Shape / 元素 / 布局 | 不含任何算子逻辑 |
| `backend/cpu` | 循环实现 | 不做形状校验、不分配内存 |
| `operator` | 校验 + 参数处理 + 分配输出 | 不写循环 |
| `graph` | 依赖关系、执行顺序 | 不做实际计算 |
| `runtime` | 执行 | 不定义算子 |

## 二、四条贯穿全局的设计原则

### 1. 实现层解耦：算子不绑定内核

```
Operator  →  CPU Backend  →  CPU + SIMD
```

`operator/sum.hpp` 只负责拆分形状、分配输出，循环全在
`backend/cpu/reduction.hpp`。换 SIMD、换并行策略都不需要动算子接口。

### 2. 算子层保持值语义，引用语义只活在两层

这是本项目最容易被误改的一条，单列一节说明。

`ops::*` 的对外签名恒为 `const Tensor<T>&` 进、`Tensor<T>` 出。
共享与引用语义**只允许出现在 `graph` 和 `runtime` 两层**，不渗进
`tensor` 与 `operator`。

具体表现：计算图的边上传递的是共享句柄（`tensor::TensorPtr<T>`），
但算子闭包里要显式解引用才交给算子：

```cpp
g.bind_op(n_shift, [](const std::vector<tensor::TensorPtr<float>>& ins) {
    return ops::shift(*ins[0], /*offset=*/1);   // ← 解引用后仍是值语义
});
```

这样做的收益：`Tensor` 保持纯值类型（深拷贝语义、无别名风险），
算子实现完全不需要知道图的存在。代价是闭包多写一个 `*`。

详见 [02-数据抽象与内存](02-数据抽象与内存.md) 的所有权模型一节。

### 3. 先正确，再优化

```
功能正确 → 建立测试 → 性能测试 → 定位瓶颈 → 优化
```

README 明确写了"不在没有 Benchmark 的情况下盲目优化"。这条不是口号——
项目里已经有两处因此改变结论：`rolling_std` 的累加器（float → double）和
`Tensor` 的默认分配器（直连 → 池化），都是先量后改。

基准基建见 [05-性能与测量](05-性能与测量.md)。

### 4. 聚焦 CPU

不引入 CUDA / GPU。CPU 侧的框架本身（数据抽象、算子、运行时、计算图）
仍有大量可深入的内容。

## 三、工程结构

```
FluxCompute/
├── include/flux/     对外头文件（header-only，src/ 仅有占位）
│   ├── tensor/       Shape、Tensor
│   ├── memory/       分配器、内存池
│   ├── operator/     算子门面（14 个算子）
│   ├── backend/cpu/  内核实现
│   ├── graph/        Node、Graph
│   ├── runtime/      Executor、ThreadPool
│   └── flux.hpp      统一入口
├── tests/            14 个测试可执行文件，注册进 CTest
├── benchmarks/       性能基准，**不注册进 CTest**（不含断言）
├── examples/         端到端示例
└── docs/             本目录
```

`tests/` 回答"算得对不对"，`benchmarks/` 回答"算得快不快"，两者分开：
基准不该让 CI 因为机器快慢而红。

### 库是 header-only 的

`src/` 下只有 `.gitkeep`。这带来一个必须遵守的约定：
**非模板的自由函数必须标 `inline`**，否则跨翻译单元会 ODR 冲突
（`operator/axis_util.hpp` 的 `compute_axis_info` 就是例子）。

## 四、当前进度

| 层 | 状态 |
|---|---|
| `memory` | 分配器 + 内存池可用，池化是 `Tensor` 默认路径。内存回收策略与静态析构顺序是已知局限 |
| `tensor` | 稳定。仅支持连续布局，`Shape` 的 stride 已算但尚无消费者 |
| `operator` | 14 个算子；`reduce` / `scan` 为通用形式，其余为专用形式 |
| `backend/cpu` | SIMD 提示已确认冗余（见 [05](05-性能与测量.md)），目标指令集策略待定 |
| `graph` | 建图、绑定、拓扑排序可用 |
| `runtime` | **仅顺序执行**。并行调度未实现 |

未完成项集中记录在 [05-性能与测量](05-性能与测量.md) 与各层文档末尾。
