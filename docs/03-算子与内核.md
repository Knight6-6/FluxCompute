# 算子与内核

覆盖 `operator/` 与 `backend/cpu/` 两层：算子怎么定义、语义怎么约定、
以及当前的优化状态。

---

## 一、结构：算子不写循环

```
operator/sum.hpp          校验形状、分配输出、转发    ← 无循环
        ↓
backend/cpu/reduction.hpp 循环实现 + SIMD 提示        ← 无形状校验、不分配
```

以 `sum` 的按轴版本为例，算子层只有三行实质代码：

```cpp
const auto info = detail::compute_axis_info(input.shape(), axis);
tensor::Tensor<T> result{tensor::Shape(info.out_dims)};
backend::cpu::sum_axis(input.data(), result.data(),
                       info.outer_size, info.axis_size, info.inner_size);
```

收益是换实现不动接口。这条已经被验证过：`reduce` / `scan` / `rolling_std`
三个新算子都是直接建在这套约定上的。

### 共享的按轴分解

`operator/axis_util.hpp` 的 `compute_axis_info` 把多维张量按 `axis` 拆成
`outer / axis / inner` 三段，供所有按轴算子复用。它取代了原本在
`sum` / `shift` / `rolling` 里各自重复的三份实现。

`axis >= dims.size()` 时抛 `std::out_of_range`，边界校验也统一在这里。

### 内核签名约定

后端内核统一为：

```cpp
void foo_axis(const T* input, T* output,
              std::size_t outer_size, std::size_t axis_size, std::size_t inner_size,
              /* 算子特有参数 */);
```

循环序有两种，按是否需要 per-slice 状态选择：

| 形态 | 用在 | 例子 |
|---|---|---|
| `o → a → i`（内层连续，可 SIMD） | 不需要 per-slice 状态 | `sum_axis` |
| `o → i → a`（每切片状态是标量） | 需要 per-slice 累加器 | `rolling_mean_axis`、`rank_axis`、`mean_axis`、`extremum_axis`、`reduce_axis`、`scan_axis` |

## 二、语义约定

这一层最容易被误改，几条约定都是显式做出的决定。

### 2.1 单位元不能有默认值

通用归约 `reduce` 与 `scan` 的单位元**必须由调用方给出**，不做 `T{}` 兜底。

看起来 `0` 是个合理默认——对求和确实如此。但求最大值的单位元是 `lowest()`，
用 `0` 会让**全负切片取到错误的 0**。整数 `T` 没有 NaN，这个错误不会被任何
NaN 检查拦住。

这个坑在写 `max` / `min` 时就踩过一次，所以通用形式直接把它做成必填参数。
测试正反两面都断言了（`test_reduce_identity_is_not_optional`）。

### 2.2 NaN 语义在两类算子上是分裂的，而且是故意的

| 算子 | NaN 处理 | 理由 |
|---|---|---|
| `sum` / `mean` / `max` / `min` / `rolling_mean` / `rolling_std` | **skipna**（跳过） | 它们知道 NaN 对各自运算意味着"不参与" |
| `reduce` / `scan`（通用形式） | **不跳过** | 拿到的是任意二元算子，无从知道它该怎么处理 NaN |

这与 pandas 一致：`sum` / `mean` 默认 `skipna=True`，而 `agg` 传自定义函数时
`skipna` 不生效。

`scan` 还有一处更细的差异：pandas 的 `cumsum` 在 NaN 处**输出 NaN 但继续累加**
（`[1, NaN, 3] -> [1, NaN, 4]`），而这里一旦吃到 NaN 之后全是 NaN
（`-> [1, NaN, NaN]`）。要 pandas 语义应当在算子层显式处理 NaN，
不该把假设埋进通用内核。差异已钉成断言。

### 2.3 空集语义

| 算子 | 空有效集（或全 NaN）的输出 |
|---|---|
| `sum` | **0**（加法单位元） |
| `mean` / `max` / `min` | **NaN** |

这是 pandas 的行为，不是不一致。

### 2.4 整数 `T` 的算术是整数算术

`mean` 是整除截断，`rank` 的并列小数被截断。这些都在头文件注释里写明了。

## 三、数值稳定性：一个差点静默上线的灾难

### 问题

`rolling_std` 最初打算沿用 `rolling_mean` 的结构，用 `T` 累加 `sum` / `sum_sq`，
方差按 `sum_sq - sum²/n` 算。数学上正确，但**存在灾难性抵消**。

### 实测（对照"先减均值"的稳定两趟算法，取最大相对误差）

| 数据量级 | float 累加 | double 累加 |
|---|---|---|
| 收益率 ~0.01 | 3.0e-07 | 5.6e-16 |
| 价格 ~100 | **3.4e-02** | 9.3e-12 |
| 价格 ~100 且波动极小 | **1.6e+03** | 2.1e-04 |
| 成交额 ~1e6 | **1.0e+00** | 3.2e-10 |

float 累加在成交额量级下误差 **100%**——等于没算。

### 取舍

累加器统一提升到 double（`long double` 除外），并让整数 `T` 也走 double，
避免 `sum_sq` 在整数上溢出。

**这个问题的危险之处在于测试测不出来**：测试用小数据、干净的整数，float 累加
完全正确。只有用真实量级的数据才会暴露。所以测试里专门加了一条数值回归，
用成交额量级（1e6）对照稳定参照，相对误差须在 1e-4 内。

### 残留局限

均值² / 方差 超过 ~1e7 时 double 也开始丢有效位，要覆盖得换 Welford 递推或
分块两趟算法。但那种数据的 mean/std 比已经超出 float 的表示能力，属于人造输入。
内核里标注了明确的改造点。

## 四、算子清单

| 类别 | 算子 | 说明 |
|---|---|---|
| 逐元素 | `add` `sub` `mul` `div` | 共用 `BinaryElementwise<T, Operation>`，形状必须相同（无广播） |
| 归约（专用） | `sum` `mean` `max` `min` | 全量 + 按轴两种形态，带 skipna |
| 归约（通用） | `reduce` | 调用方给二元算子与单位元，不 skipna |
| 扫描 | `scan` | 前缀扫描，只提供按轴形态 |
| 序列 | `shift` `rolling_mean` `rolling_std` | 按轴、增量滑窗 O(n)、skipna |
| 排序 | `sort` `rank` | 沿轴稳定排序 / 平均名次 |

`max` / `min` 共用 `detail::extremum_all` / `extremum_axis` 骨架
（只差比较符与单位元）；`sum` / `mean` / `max` / `min` 的按轴路径共用
`compute_axis_info`。

### 已知的复杂度边界

`rank_axis` 是**每切片 O(N²)** 的计数法，源码注释写明"正确性优先"。
对横截面 rank（几千个标的）没问题，但**不要对 1M 元素的长序列做 rank**——
那是 1e12 次比较量级。需要的话应换基于排序的 O(N log N) 实现。

## 五、优化状态

### SIMD 提示是冗余的

项目从建立起就在内核上挂 `#pragma omp simd`，但从未验证过收益。
对照实验（同一源文件编两份，一份链 OpenMP、一份不链）：**两者结果在噪声内相同**。

编译器的向量化报告给出了原因：

```
基线 SSE2：      loop vectorized using 16 byte vectors   ← -O3 已经向量化了
-march=native：  loop vectorized using 64 byte vectors   ← AVX-512
```

`-O3` 的自动向量化本来就命中了这些循环，pragma 没有额外贡献。

### 真正的杠杆是指令集

`-march=native` 带来的是数量级差异：`sum_all` 1M 从 0.63 ms 降到 0.04 ms（约 14 倍）。

**但这带来可移植性问题**（二进制不能在旧 CPU 上跑），需要单独决策，
不能靠加 pragma 解决。候选方案：交给使用者指定 / 运行时分发（function
multiversioning） / 保持基线。**尚未决定。**

### 没有做、也不该现在做的事

`reduce` / `scan` / `extremum` 的内核刻意**不加** simd 提示：任意二元算子未必
可向量化，前缀扫描天然存在循环携带依赖。向编译器做无依据的承诺比不优化更糟。

按"先正确，再优化"，这些留到基准确认它们是瓶颈后再单议。
基准见 [05-性能与测量](05-性能与测量.md)。
