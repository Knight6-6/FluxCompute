# 性能与测量

`benchmarks/` 回答"算得快不快"，`tests/` 回答"算得对不对"。本文记录基准
基建的设计、已得到的关键结论，以及**测量方法本身的坑**——没有后一部分，
前面的数字都不可信。

---

## 一、基准基建

与 `test_util.hpp` 同源：单头文件、无外部依赖（不引 Google Benchmark）。

```bash
cmake --build build
./build/benchmarks/bench_executor          # 图执行开销
./build/benchmarks/bench_memory            # 分配器对比
./build/benchmarks/bench_elementwise       # 内核吞吐（OpenMP 开）
./build/benchmarks/bench_elementwise_noomp # 同上，对照组
```

**务必用 Release 构建**（根 `CMakeLists.txt` 默认就是）。Debug 下的数字没有意义。

### 三个刻意的取舍（`bench_util.hpp`）

1. **取最小值而非均值。** 微基准里的噪声（调度、频率抖动、其他进程）只会让
   某次测量变慢，不会变快，所以最小值最接近"没有干扰时的真实成本"。均值
   反而把噪声混进了信号。
2. **每组先跑 warmup。** 首次触碰内存要建页表、填缓存，第一次的数字系统性偏慢。
3. **`keep()` 阻止死代码消除。** 见下文第三节第一条。

### 不注册进 CTest

基准不含断言，不该让 CI 因为机器快慢而红。它们是普通可执行文件。

## 三、测量方法本身的坑

这一节比上面的数字更重要。

### 3.1 编译器会把你想测的东西优化掉

第一版内存基准用 `std::vector<float, Alloc> v(elems);` 制造分配，测出
"1MB 直连分配 200k 次只要 0.127 ms"（25 ns/次）——物理上不可能。
原因是缓冲区内容无人观察，**分配和清零都被合法消除了**。

更隐蔽的是：池化那一路因为改动全局状态而无法被消除，于是**两边根本不在测
同一件事**，得出"池慢 323 倍"的结论，与真相（池快 1.75~3 倍）方向完全相反。

**对策**：直接调 `allocate`/`deallocate` 并触碰首尾元素，让指针逃逸
（`bench_util.hpp` 的 `keep()`）。

> **没有逃逸的测量等于没测。**

### 3.2 参照实现不能就是被测算法

验证 `rolling_std` 精度时，第一版参照实现用的也是 `double` 累加的同类公式，
于是被测与参照完全相同，误差必然是 0——循环论证，白测一轮。

换成"先减均值"的稳定两趟算法后，才看到真实误差。

### 3.3 编译参数不同，结论会反过来

同一个 `sum_all`：

```
项目当前参数（-O3，基线指令集）   0.63 ms
加 -march=native                 0.04 ms
```

拿后者去和别的实现比，会得出完全错误的结论。**基准数字必须标注编译参数。**

### 3.4 基准要覆盖真实的调用形态（代价最大的一条）

内存池最初被判定为"不值得启用"，依据是：

```
ops::mul 1M = 0.13 ms，分配在其中的占比很小
```

这个判断在**单算子**场景完全正确。但它漏掉了图执行特有的形态——
每轮 `run()` 都重建全部中间张量，于是分配从"小占比"变成了"主要成本"
（因为反复 `mmap`/`munmap` 触发缺页）。

两个场景的结论完全相反。**基准如果只测单算子，就会得出与真实使用相反的结论。**

### 3.5 工具用错比不用更糟

`rank` 是每切片 O(N²) 的计数法（源码注释写明了"正确性优先"）。
拿 1M 元素的长序列去跑 `rank` 基准，等于要求 1e12 次比较——进程直接卡死，
只能杀掉重来。**跑之前先看一眼目标算子声明的复杂度。**

## 四、案例：图执行的 75% 时间花在缺页上

这是目前信息量最大的一次定位，完整过程留在这里作为方法论样本。

### 现象

```
裸 ops::shift + 裸 ops::mul 之和        1.09 ms
同样两个算子放进图里执行                2.5 ~ 4.3 ms
图中 1 个算子                          0.15 ms   ← 与裸调用一致
```

尺寸扫描确认额外开销**随数据规模线性增长**（每级 4 倍尺寸 → 4.3~4.85 倍开销），
约 2.8 ns/元素——是逐元素的工作量，不是固定开销。

### 定位

量缺页：**2016 次/轮**。而 2016 × 4KB = 8.06 MB，正好是两个 4MB 输出张量。

根因：每次 `run()` 结束时的 `values_.clear()` 释放上一轮中间张量，下一轮新建
同尺寸张量时 glibc 走 `mmap`/`munmap` 路径，每一页都要重新 fault。

### 验证（决定性，不是推断）

用 `MALLOC_MMAP_THRESHOLD_` 强制 glibc 走堆分配：

```
基线        4.39 ms/轮   缺页 2016/轮
禁用 mmap   1.15 ms/轮   缺页    0/轮
```

而禁用 mmap 后的 1.04 ms 与"裸 shift 0.93 + 裸 mul 0.15 = 1.09 ms"几乎完全吻合
——说明**图执行本身没有开销，之前看到的全是缺页**。

### 修法

| 修法 | 效果 | 取舍 |
|---|---|---|
| `mallopt(M_MMAP_THRESHOLD, 64MB)` | 4.39 → 1.15 ms | 一行搞定，但**改变宿主进程的全局分配器行为**——header-only 库偷偷干这个不可接受 |
| `Tensor` 改用 `PooledAllocator` | 4.39 → **0.99 ms** | 只影响本库自己的分配，作用域正确 |

采纳后者。详见 [02-数据抽象与内存](02-数据抽象与内存.md)。
